# Internacionalización

Sin librería. El locale vive en la URL, así el HTML prerenderizado y la app hidratada siempre coinciden y cada idioma tiene su propia URL indexable.

| URL                              | Locale                      |
| -------------------------------- | --------------------------- |
| `/`, `/about`, `/blog/x`         | `es` (default, sin prefijo) |
| `/en`, `/en/about`, `/en/blog/x` | `en`                        |
| `/es/about`, `/fr/about`         | no existen → 404            |

## Piezas

- **`src/shared/i18n/config.ts`** es la fuente única de `LOCALES`, `DEFAULT_LOCALE` y `LOCALE_TAGS`. Lo leen rutas, prerender, SEO y sitemap. Helpers: `localizePath`, `stripLocale`, `localeFromPathname`, `isLocale`.
- **`src/app/routes.ts`** monta cada página una vez por locale con un `id` propio (`es.about`, `en.about`). No hay segmento opcional `:lang?`: una URL de idioma inválido nunca llega a una página.
- **Textos de cada feature** en `src/features/<x>/i18n/`: `es.ts` define el tipo (`BlogText = typeof es`), `en.ts` se tipa con él e `index.ts` expone `blogText` (`LocaleTexts<BlogText>`) y `useBlogText()`. Si falta una clave o un locale, el build falla.
- **Diccionario global** (`src/shared/i18n/dictionaries/`): solo el chrome del sitio (`nav`, `theme`, `consent`, `footer`). Mismo esquema: `es.ts` define `Dictionary`.
- **`useI18n()`** devuelve `{ locale, t, href }` con el diccionario global. `href('/about')` produce `/about` o `/en/about` según el locale activo.
- **`useLocaleText(texts)`** elige el locale activo de un `LocaleTexts<T>`. Cada feature lo envuelve en su hook, así `shared/` no conoce a ninguna feature.
- **En `meta`/`loader`**, donde no hay hooks: `blogText[locale]` (exportado por `#features/blog`) y `getDictionary(locale)` para el chrome.
- **`getRouteLocale(request)`** da el locale en un `loader`. Quita el sufijo `.data` de las peticiones de datos: `/en.data` es `en`.
- **`<html lang>`** se calcula en `root.tsx` desde la URL.
- **Selector de idioma** (`site-header.tsx`): enlaza a la misma página en cada locale, con `hrefLang` y `lang`.

## Por qué los textos viven en cada feature

Borrar o copiar una feature es borrar o copiar su carpeta, textos incluidos. Cada ruta carga solo los textos de su feature, no el diccionario completo. `shared/` aporta el mecanismo (`LocaleTexts`, `useLocaleText`) sin importar features, así la regla de dependencias se mantiene.

## Contenido

El contenido largo (posts) vive en `src/features/blog/content/<locale>.json` y se valida con zod en el build (`src/features/blog/types.ts`). Los slugs se comparten entre locales: así hreflang empareja las versiones. `src/features/blog/api/posts.test.ts` lo verifica.

## Agregar un idioma

1. Agrega el código a `LOCALES` y su tag a `LOCALE_TAGS` en `src/shared/i18n/config.ts`.
2. Crea `src/shared/i18n/dictionaries/<código>.ts` tipado con `Dictionary` y regístralo en `src/shared/i18n/index.ts`.
3. Crea `src/features/<x>/i18n/<código>.ts` en cada feature y agrégalo a su `index.ts`. TypeScript señala cada feature que falte (`LocaleTexts` exige todos los locales).
4. Crea `src/features/blog/content/<código>.json` y agrégalo al mapa `RAW` de `src/features/blog/api/posts.ts`.
5. `npm run build`: rutas, prerender, hreflang y sitemap se generan solos.

## Quitar i18n (sitio de un solo idioma)

Deja `LOCALES = ['es']`. El prefijo desaparece, no se emiten alternates (`buildMeta` solo los pone con más de un locale) y el selector muestra un solo enlace. Puedes borrarlo de `site-header.tsx`.
